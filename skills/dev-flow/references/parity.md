# 照已有实现做

适用场景：照着另一端（Android 和 iOS 互相对照、Web 和 App 互相对照）、旧版本或兄弟项目的现成实现来做，或者照带交互逻辑的原型（比如 HTML 原型）来做。

1. **先确认参考源是最新的。** 读哪个分支，按档案的「参考源」；档案没写、远端最近有提交的分支又不止一个的，主流程第 3 步问用户。参考仓库先 fetch，看本地比远端落后多少。落后了就直接读远端，比如 `git show origin/<分支>:<路径>`，别拿旧代码来对齐。大仓库或带 LFS 的仓库只用轻量的只读命令。档案里有特殊要求的，按档案来。
2. **以源码为准，而且要读完整。** 设计文档、注释、PR 描述都可能和代码对不上，界面层尤其要核对源码。相关代码要完整读一遍，别只看几个片段就开始写。参考代码多的，可以先让子代理找出相关文件，但要对齐的代码自己读原文，不照子代理的摘要写。
3. **参考自己说的和做的要对一遍。** 参考里写给用户看的说明（文案、课程介绍、规则说明）、需求文档，和参考代码实际怎么做的，逐条对。对不上的不默认以代码为准，列进差异清单，问用户以哪个为准。比如原型的课程说明写「收 3 秒、松 3 秒」，原型的算法却按波形走。
4. **逐点对齐。** 功能、数值、文案（含多语言）、交互逻辑、视觉（布局、颜色、尺寸）都保持一致，只把控件和技术栈换成本端的写法。数值顺着引用追到定义处取原值，定义可能在别的模块，甚至别的仓库；不估，也不拿本端相近的值顶替。本端没有对应变量的，记下来问用户。
5. **先列差异清单再动手。** 三类都列：参考实现有而本端没有的、本端有而参考实现没有的、两边都有但行为不一样的。容易漏的逐项核对：显示和隐藏的条件（按设备型号、地区、登录状态区分的开关）、空数据、加载中和出错时的样子、文案和多语言、本地缓存、权限。参考实现看起来有 bug 的，不照抄也不擅自修，列出来问用户。拿不准的放到主流程第 3 步问用户。清单写进拍板摘要，每条一个编号，验收时逐条核对。
6. **拍板摘要每条标来源。** 照参考的标「照参考」（照原型做的写「照原型」）；参考里没有、自己加的标「我补的」；和参考不一样的标「我改的」。补的和改的都写上理由，让用户拍板，不默默加、不默默改。
7. **两端对照着验。** 参考端能跑起来的（另一端的 App、旧版本的包），同一个场景两端各跑一遍：界面截两端的图，并排放进测试结果文档对比；逻辑对比两边的日志或输出。跑不起来的，按差异清单逐条对照参考源码里的数值。
8. **有意不一致的记进档案。** 平台做不到的、用户拍板不跟的，记进档案「参考源」一节：哪里不一样、为什么，并告诉用户；以后对齐时照着跳过，不再改回去。同一节记下这次对齐到参考仓库的哪个提交，下次跟进时用 `git log <这个提交>..origin/<分支>` 看参考端后来改了什么。
9. **注释里不引用参考实现**，比如「对齐某端某类第几行」。参考只是参考，注释只解释本端代码本身。档案另有要求的除外。
