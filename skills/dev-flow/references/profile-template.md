# 项目档案：生成方法与模板

档案是写给你自己看的工作手册，不是项目介绍。只写会影响怎么干活的事实，写短、写准。

## 生成规则

- **先读对应的技术栈指南**：[stacks/](stacks/) 下有 ios.md、android.md、flutter.md、web.md、backend.md，按里面的方法推断。一个仓库有多个技术栈时（比如 Flutter 宿主里的原生 iOS），用到哪个就读哪个。没有对应指南的技术栈，用下面的通用推断清单。
- **只写本项目特有的**：技术栈通用的做法和坑，指南里已经有了，档案里不再重复。
- **位置**：仓库根目录的 `.claude/project-profile.md`。一个仓库里有多个子项目时，公共的内容写在根目录那份，各子项目特有的写在各自目录下，比如 `ios/.claude/project-profile.md`。读的时候沿途的都读，离改动近的优先。
- **先确认会不会被提交**：生成前检查 `.claude/` 有没有被 git 忽略（`git check-ignore`）。没被忽略的，先把档案加进 `.git/info/exclude`（只在本机生效的忽略清单，不改动 `.gitignore`），保证不会被误提交。这只是先挡住，不算定了只留本机：「要不要共享」照样标「待问」，第 3 步问用户要不要改成提交给团队共享。
- **能推断的自己填**，并注明来源，例如「来自 package.json 的 scripts」。
- **推断不了的**，标成 `待问`，在第 3 步一起问用户。
- **验证命令的耗时**：几秒的命令当场跑一次，确认能用并记下耗时，跑不通就写明原因。要几分钟以上的（比如原生整包编译），不专门为了计时去跑：先写「待测」，按慢命令处理（放到阶段末尾），等第一次正式验证时顺便记下耗时。
- **已有的规范文件只引用、不复制**，比如 CLAUDE.md、AGENTS.md、CONTRIBUTING。

## 通用推断清单（没有对应技术栈指南时用）

| 看哪里 | 能推断出什么 |
|---|---|
| package.json 的 scripts、Makefile、justfile、Taskfile | 构建、测试、lint、运行命令 |
| tsconfig、eslint、prettier、ruff、golangci、swiftlint、detekt | 类型检查和代码规范 |
| Podfile、*.xcodeproj、build.gradle、pubspec.yaml、go.mod、Cargo.toml、pyproject.toml | 技术栈、依赖管理，以及新建文件或加依赖后要做的登记 |
| 目录和文件命名、公共基类、依赖和 import | 架构分层、绑定和异步方式、范例文件 |
| CI 配置（.github/workflows、.gitlab-ci.yml 等） | 项目认可的验证命令 |
| 测试目录是否存在、测试数量 | 测试策略 |
| CLAUDE.md、AGENTS.md、CONTRIBUTING、README | 已有约定 |
| 最近 200 条 git log、`git branch -a` | 提交信息格式、用过的全部类型、分支命名和合并方式 |
| docs/ 等文档目录 | 文档放在哪里 |

## 模板

```markdown
# 项目档案：<项目名>

## 技术栈
- 技术栈指南：<stacks/ios.md 等；有多个就都列上>
- <语言、框架、关键依赖，一两行>
- 架构和写法：<分层方式、绑定和异步用什么、公共基类，新代码照哪个范例文件写>
- 改动边界：<哪些目录能改，哪些不能碰>

## 验证命令
| 用途 | 命令 | 耗时 | 频率 |
|---|---|---|---|
| 类型检查 | ... | ~5 秒 | 每改完一块 |
| 单测 | ... | | |
| 构建 | ... | | 阶段末尾、提交前必须通过 |
| 运行 | ... | | |
<怎么判断成功或失败、常见的假失败>

## 测试策略
<已有的自动化测试怎么跑，没有就写「不写测试代码」；端到端验证用什么工具自动操作（点按、截图、抓日志）；哪些步骤必须人工配合，比如连接设备、登录>

## 界面验证
<截图和点按用什么工具、本机实际装了哪些、模拟器能不能跑；没有界面就写「无」>

## 日志与调试
<用哪个日志库、测试用的包里哪些日志级别看得到、怎么抓日志>

## 测试报告
<不写就用 test-report.md 里的默认位置，不用为这项问用户；项目另有要求时才写：放在哪（必须在仓库外）、怎么打开>

## 设计稿
<不写就用 ui-work.md「设计稿放哪」里的默认位置，不用为这项问用户；项目另有要求时才写：放在哪（必须在仓库外）、怎么打开>

## 新建文件、加依赖后要做的事
<比如：改工程文件、pod install、重新生成代码、注册路由>

## 约定
- 规范文件：<CLAUDE.md 等的路径>
- 文档目录：<路径和组织方式>
- 提交信息：<从 git log 推断的格式和实际用过的全部类型，比如 feat/fix/docs/chore/refactor，给一个例子>
```
