# 中、大规模：拍板后换新窗口实现

调研和问答很占上下文。拍板后接着在同一个窗口实现，做到一半容易触发自动压缩，细节会丢。所以中、大规模在用户说开工后，当前窗口只写拍板记录，实现放到新窗口做。

```
当前窗口：调研 → 拍板 → 写拍板记录（大规模再加总纲）→ 给开场白，停下
新窗口：  （大规模先写阶段 1 文档）→ 写代码 → 编译 → 验证 → 收尾
```

## 当前窗口：写拍板记录、给开场白、停下

- 拍板记录写成一份文件，放在档案约定的文档目录，档案没写的放 `docs/`。大规模放进这个任务的子目录，和总纲放在一起（总纲见 [large-work.md](large-work.md)）。中等任务不写总纲。
- 写到一个没看过之前对话的新会话也能直接照着做：
  - 拍板摘要原文，保留编号，包括用户的回答和默认做法；
  - 调研查到的关键事实和出处（文件和行号）、照哪个已有实现、影响到哪些地方；
  - 要改的文件和接口；
  - 验收清单，最后一条是端到端验证；
  - 还没解决、实现时要留意的问题；
  - 末尾一段「新窗口要做」：这是中等还是大规模；用待办清单跟踪；写测试结果文档，动笔前先读 dev-flow 的 references/test-report.md，照它的格式写，按拍板摘要编号逐条核对；测试结果先告诉用户，再做完成前审查（派一个审查子代理，只给这次的改动，不用 `/code-review`）；提交先问用户，拍板记录里定的提交信息格式不等于同意提交。新窗口一般只读拍板记录，这些规矩靠这一段带过去。
- 不改代码。写完给用户一句可以直接粘贴到新窗口的开场白，然后停下。比如：
  - 中等：「用 dev-flow 继续：读 docs/xxx-拍板记录.md，按里面的拍板结果从第 4 步开始实现」
  - 大规模：「用 dev-flow 继续：读 docs/xxx/总纲.md 和 docs/xxx/拍板记录.md，写阶段 1 文档，然后实现阶段 1」
- 拍板记录和总纲先不提交，收尾时和代码一起问。

## 新窗口：从第 4 步开始

- 先读档案和拍板记录（大规模还有总纲），再读记录里列的关键文件。
- 大规模先写阶段 1 文档。阶段文档、代码、编译、验证都在这个窗口一路做完，不再换窗口。
- 拍板结果直接照做：不重新调研，不重新问已经拍板的事。
- 第 4 步记下 `git status` 时，拍板记录、总纲、档案是这个任务的，不算别人的改动。
- 发现记录和代码对不上，按主流程第 4 步「动手后发现事先没查到的情况」处理。
- 之后照常验证、审查、收尾；汇报时按拍板记录里的摘要编号逐条核对。
- 提交照样先问用户；拍板记录里定的提交信息格式不等于同意提交。
