# 修 bug

核心：先找到根因再修。没有能稳定复现问题的反馈回路之前，不要看着代码猜。

## 1 建反馈回路

先找一个办法，能对这个 bug 给出「失败 / 通过」的信号，越快、越稳定越好。按下面的顺序找：
- 项目里已有的、能复现这个问题的测试
- 用自动化工具操作 App（点按、截图、看日志）复现
- 一个脚本：用 curl 调接口、跑一遍命令行对比输出、无头浏览器脚本
- 重放抓到的请求、日志或数据
- 某一步实在自动化不了（比如要连接实体设备）：只请用户做那一步，其余照常自动复现

不往项目里加测试代码；需要写脚本复现的，写成一次性脚本，放在测试结果目录里，和报告放在一起，方便以后复测。

**回路建好的标准**：能说出一条实际跑过的命令或一组固定操作（测试命令、脚本、curl、自动化点按），同时满足这四条：
- 走的是出 bug 的那条路径，查的是用户说的那个症状，而不是一个相似的症状；修好后会变成通过。
- 每次结果一致。偶发的 bug 先想办法提高复现率，比如循环执行、加大压力、调整时序，直到复现率稳定；复现了没有、修好了没有，都按多次运行的结果判断。
- 尽量快，后面要反复跑它。
- 不用人守着就能跑。自动化做不到的那一步例外，比如连接实体设备，或者震动强弱这类只能靠人判断的结果，只请用户做那一步。

达不到就不列假设、不改代码，也不看着代码猜原因；报错、调用栈、日志这类现成的证据可以先读，帮着找出 bug 走的路径。实在建不出回路，就说明试过哪些办法，向用户要环境、日志或数据；还是建不成的，拿已有的证据按第 2 步往下查，修完只能说「改完了、还没验证」。

**缩到最小复现**：复现之后，一次去掉一个输入、步骤、配置或数据，每去掉一个就重跑回路，只留下去掉后就不再复现的；缩完再跑一遍，确认还能复现。尽量在副本上缩。改了仓库里的文件，缩完只用改文件工具撤回自己改的那几处，不用 `git checkout`、`git stash`，免得把别人没提交的改动一起抹掉。仓库外的数据（账号、设备、服务端上的）删了恢复不了的不动。剩下的越少，第 3 步要怀疑的地方越少。缩不动或太费时的（比如每跑一次都要用户连一次设备，或者跑一次要好几分钟），说明原因再往下走。

## 2 收集证据

- 完整读完报错信息和调用栈，记下文件、行号、错误码。
- 看最近改了什么：`git log`、`git diff`，以及依赖和配置的变化。
- 找一个能正常工作的相似场景，逐条列出它和出问题的场景之间的差异，再小的差异也列上。
- 多个组件串联的（比如客户端 → 接口 → 数据库，或构建 → 签名 → 发布），在每个组件的边界打日志，看数据从哪一层开始不对。
- 性能问题，先测量（计时、性能分析工具、查询计划），再下结论。

## 3 假设与验证

- 列出 3～5 个能被证伪的假设，按可能性排序。每个都写成「如果原因是 X，那么在 Y 处应该能看到 Z」的形式，先用日志或检查确认是哪个原因，确认了再改代码；实在没法观察的，才用小改动去试。
- 验证之前，先把排好序的假设列给用户看一眼：用户可能知道哪个更可能，或者哪个已经排除了。这是告知，不是提问：不用提问工具，不停下等回复，列完接着按自己的排序验证。
- 一次只验证一个假设，一次只改一个变量。
- 临时加的调试日志统一加一个前缀（比如 `[DEBUG-a4f2]`），用档案里规定的日志方式来打。收尾时搜这个前缀，就能一次删干净。

## 4 修复

- 只改根因所在的地方。顺带发现的其他问题记下来。
- 用第 1 步的回路确认修好，缩过复现的，还要用没缩的原始场景再跑一遍；再按主流程第 5 步做端到端验证；项目已有测试覆盖的，跑一下相关测试。
- 测试结果文档里写上修之前复现的结果和修之后的结果。

## 5 两个该停下来的时刻

- **猜了两次都没修好**：停止猜测，回到第 2 步加日志拿数据。
- **按证据修了三次还没好**，或者每修一次都在别处冒出新问题：多半是设计本身有问题。停下来和用户讨论要不要调整结构，不要继续打补丁。

## 6 收尾

- 删掉仓库里所有临时调试日志；一次性脚本留在测试结果目录，不进仓库。
- 汇报时写明最终确认的根因。
- 根因如果是项目特有的坑（环境、构建、平台行为），追加进档案的危险信号表。
