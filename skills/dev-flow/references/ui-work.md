# 涉及界面时

## 先确定设计来源

按精度从高到低找，找到第一个能用的就用它：

1. **结构化的设计数据**：已接入 Figma、MasterGo 等的 MCP，就直接读图层、变量和切图，不要看图估算。
2. **另一端的现成实现**：布局 XML、组件代码、CSS。把它当作精确规格逐个数值还原，查证方法见 [parity.md](parity.md)。
3. **带标注的设计图**：直接用标注的数值。
4. **纯截图**：能量的用脚本量，不凭眼睛估：颜色读像素值，尺寸按截图倍率换算（比如 @3x 的截图，像素 ÷ 3 = pt）。压缩过的图、阴影、渐变这类量不准的才估。估出来的值列在测试结果文档里，标上「估」，代码里不写；实现后通过截图对照来修正。
5. **什么都没有**：自己设计，见下文「自己设计」。

照另一端做的任务，以另一端的实现为准，设计稿只作参考；两者对不上的，列进差异清单问用户。

## 还原已有设计

- **视觉优先一致**：布局、颜色、字号、间距、圆角逐项对齐。换成本端的原生控件，不等于可以改外观。
- **图标和图片用原始资源**：从设计稿导出，或者从另一端的资源转换，不拿系统图标或相近的图顶替；拿不到的，列出来问用户。
- **用项目已有的配色和字号变量**，不写死数值。变量的值要和设计完全一致才用，不能只看名字像（比如页面底色的变量，不能拿来当弹窗底色）。找不到对应变量的，记下来向用户提。
- **先搜再建**：按钮、卡片、导航栏这类组件，先找项目里有没有现成的。现成的和设计对不上时，不要为了对上去直接改公共组件（会影响用到它的其他页面），列出来问用户。

## 自己设计（没有设计稿时）

这时你同时是产品经理和 UI 设计。产出是给自己实现用的，要的是精确，不需要包装得好看。

1. **先定视觉规范**：
   - 已有页面的 App：从其他页面的代码里提取现成的用法（主题色、字号、圆角、间距、常用组件），照着用，新页面才和其他页面一致。
   - 全新 App，一个页面都还没有：第 3 步问用户有没有品牌色、喜欢的风格或参考的 App、要不要深色模式。没有偏好的，以平台默认规范为底（iOS 用系统字体和标准字号层级，Android 用 Material 3），由一个主色配出整套颜色，间距统一用 4 的倍数。第 4 步先出一页规范稿（色板、字号层级、按钮、卡片、输入框），和关键页面一起请用户确认；确认后先在代码里建好主题变量和基础组件，再做页面。
   - 定下的规范写进档案；内容多的，单独写一个 design.md 放在档案旁边，档案里写上路径，下次直接复用。
2. **列出页面清单和跳转流程**。每个页面把状态列全：正常、空数据、加载中、出错、没权限或未连接、边界数据。
3. **每个显示字段写清四件事**：数据从哪来、单位、显示格式、没数据时显示什么。
4. **出 HTML 高保真稿**：用第 1 步定下的数值。手机端套上真机尺寸的外框。图标优先用平台自带的图标库（SF Symbols、Material Symbols）。给用户看一眼，确认方向。拿不准的设计点，可以画 2～3 个变体让用户挑。稿子放进设计稿目录（见下文「设计稿放哪」），回复里给链接。看稿、挑变体放在第 3 步，和其他问题一起拍板。
5. **实现时照搬 HTML 稿里的精确数值**，翻译成本端控件。

## 设计稿放哪

设计稿是后面照着做、截图对照时要反复翻的依据，和「某一次测完」的测试结果不是一类东西，所以单独放，不放进测试结果目录。

- **放在仓库外**，不进 git，长期保存。所有项目共用一个根目录，别的项目要参考也找得到。位置按档案里写的（档案指定的位置也必须在仓库外）。档案没写的，用默认位置：

  ```
  ~/Documents/Designs/
  ├── README.md                目录约定，没有就照这一节新建
  └── <项目名>/                 仓库文件夹的名字
      ├── 设计稿清单.md          这个项目的所有设计稿，一份一行：日期、主题、结论、链接
      └── <日期>-<主题>/         比如 2026-10-20-设计方向稿、2026-10-22-规范稿
          ├── index.html        设计稿网页
          └── ...               稿子用到的图片等
  ```

  - 同一天同一个主题再出一版，目录末尾加 `-2`、`-3`，不覆盖之前的。名字里不用空格。
  - 出完一份，在「设计稿清单.md」末尾追加一行，结论先写「待定」；用户拍板后只改这一行的结论（比如「选了 A，深浅两套都做」），别的行不动。没有这个文件就新建，第一行写表头 `| 日期 | 主题 | 结论 | 链接 |`。
- **看稿**：在 `~/Documents/Designs/` 起本地 http 服务（端口被占就换一个），回复里给这份稿的 http 链接；往期的稿、别的项目的稿也能在浏览器里点开。
- **定下的规范**：照「自己设计」第 1 步写进档案或 design.md，写明出自哪份稿；截图对照时和这份稿并排比。

## 截图对照

- **一次做一屏**：实现 → 截图（用档案里写的截图工具）→ 和设计稿并排（照另一端做的，就和另一端的截图并排）→ 逐项列出差异 → 修改，再截图对比，直到没有差异。对比时能量的用脚本量，量的是没压缩的原图（报告里的截图压缩过，颜色和倍率都不准），不凭眼睛看「差不多」。改不掉的（比如平台的字体渲染、系统控件自带的样式），写进测试结果文档，说明原因。
- **状态和环境都要截**：每屏的正常、空数据、加载中、出错都截；能切换的，再看一下小屏、深色模式和文案最长的那种语言。
- **修改顺序**：布局 → 尺寸和间距 → 颜色 → 字体 → 细节。
