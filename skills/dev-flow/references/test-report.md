# 测试结果文档

测完统一出一份，给用户看测试结果。每个测试点都要有对应的截图或日志，以及说明。

## 存放

- **放在仓库外**，不进 git，不会被提交，也不会被推送；长期保存，以后能翻出来对照。
- 位置按档案里写的（档案指定的位置也必须在仓库外）。档案没写的，用默认位置：

  ```
  ~/Documents/TestReports/
  └── <项目名>/                   仓库文件夹的名字
      ├── 报告清单.md              这个项目的所有测试报告，一份一行：日期、主题、结论、链接
      └── <日期>-<主题>/           比如 2026-10-15-固件升级完成页，主题用几个中文字说清测的是什么
          ├── report.md           报告正文
          ├── index.html          同内容的网页版
          ├── 01-<简短名>.png      截图：两位序号对应「一览」里的编号，简短名几个字说清是什么
          └── 01-<简短名>.log      这一项的日志摘录，有才放
  ```

  - 同一天同一个主题再测一次，目录末尾加 `-2`、`-3`，不覆盖之前的。名字里不用空格。
  - 写完在「报告清单.md」末尾追加一行，旧的行不改；没有这个文件就新建，第一行写表头 `| 日期 | 主题 | 结论 | 报告 |`。
- 截图和日志跟报告放在同一个目录，报告里用相对路径引用。
- 写完告诉用户报告在哪、怎么打开。档案没写的，默认在报告旁边生成一份同内容的 index.html，在项目文件夹（`~/Documents/TestReports/<项目名>/`）起本地 http 服务（端口被占就换一个），回复里给这次报告的 http 链接；往期的报告也能在浏览器里点开。

## 格式

全文用大白话，少用术语；非用不可的，第一次出现时在括号里解释。不懂技术的人只看开头的结论和一览就能明白，开发再看后面的详情。

```markdown
# <功能名> 测试结果（<日期>）

**结论**：<一句大白话：能不能用、还差什么>
**需要你做的**：<没有就写"无">
- <比如：在设备上感受震动强度合不合适（见第 5 项）>
**测的版本**：<分支> 的 <提交号>（另有没提交的改动就写明）；拍板记录在 <路径>（没有就不写）

## 一览
| # | 测了什么 | 结果 |
|---|---|---|
| 1 | <一句话说清场景> | ✅ 通过 |
| 2 | …… | ⚠️ 需要你确认 |

通过 X 项，没通过 X 项，需要你确认 X 项，没能测 X 项（原因：……）

## 说好的都做到了吗（中、大规模）
拍板摘要每段一张表，段名写在表头，下面照摘要的编号 1、2、3 往下列，每行写这条的小标题；不合并、不改写、不跳号。依据、影响范围、已知风险三段是背景，不列。开工后又定下的事，另起一张「后来加的」表，也从 1 编号。

| 做什么 | 结果 | 说明 |
|---|---|---|
| 1. <这条的小标题> | ✅ 做到 / ❌ 没做到 / 🔄 有调整 | 没做到或有调整的写原因 |
| 2. …… | | |

| 不做什么 | 结果 | 说明 |
|---|---|---|
| 1. …… | | |

## 每一项的详情

### 1. <测了什么>
- **怎么测的**：……
- **应该看到**：……
- **实际看到**：……
- **结果**：✅ 通过 / ❌ 没通过 / ⚠️ 需要你确认 / ⏭️ 没能测
- **截图**：![<测了什么>](01-<简短名>.png)
  <一句话说明看图里的哪里>
- **日志**（给开发看）：
  ```
  只摘和这一项相关的几行
  ```

### 2. ……

## 没通过的和后续
- 每个没通过的项：原因、怎么修的。修完要重测，并更新上面的结果。

## 测试环境（给开发看）
- 设备、系统版本、构建方式
```
