# 测试结果文档

测完统一出一份，给用户看测试结果。每个测试点都要有对应的截图或日志，以及说明。

## 存放

- **放在仓库外**，不进 git，不会被提交，也不会被推送。
- 位置按档案里写的（档案指定的位置也必须在仓库外）。档案没写的，放到默认位置 `/tmp/claude-test-reports/<项目名>/<日期>-<主题>/`（重启电脑会被清理）；同名目录已经存在、又不是这次自己建的，就在末尾加序号，不覆盖别人的。
- 截图和文档放在同一个目录，文档里用相对路径引用图片。
- 写完告诉用户文档在哪、怎么打开。档案没写的，默认在文档旁边生成一份同内容的 index.html，在测试结果目录起本地 http 服务（端口被占就换一个），回复里给 http 链接，方便在浏览器里看图。

## 格式

全文用大白话，少用术语；非用不可的，第一次出现时在括号里解释。不懂技术的人只看开头的结论和一览就能明白，开发再看后面的详情。

```markdown
# <功能名> 测试结果（<日期>）

**结论**：<一句大白话：能不能用、还差什么>
**需要你做的**：<没有就写"无">
- <比如：在设备上感受震动强度合不合适（见第 5 项）>

## 一览
| # | 测了什么 | 结果 |
|---|---|---|
| 1 | <一句话说清场景> | ✅ 通过 |
| 2 | …… | ⚠️ 需要你确认 |

通过 X 项，没通过 X 项，需要你确认 X 项，没能测 X 项（原因：……）

## 说好的都做到了吗（中、大规模）
按拍板摘要的编号逐条列，不合并、不改写、不跳号。
| 编号 | 说好的（拍板摘要原文） | 结果 | 说明 |
|---|---|---|---|
| 1 | …… | ✅ 做到 / ❌ 没做到 / 🔄 有调整 | 没做到或有调整的写原因 |

## 每一项的详情

### 1. <测了什么>
- **怎么测的**：……
- **应该看到**：……
- **实际看到**：……
- **结果**：✅ 通过 / ❌ 没通过 / ⚠️ 需要你确认 / ⏭️ 没能测
- **截图**：![<测了什么>](1-<简短名>.png)
  <一句话说明看图里的哪里>
- **日志**（给开发看）：
  ```
  只摘和这一项相关的几行
  ```

### 2. ……

## 没通过的和后续
- 每个没通过的项：原因、怎么修的。修完要重测，并更新上面的结果。

## 测试环境（给开发看）
- 设备、系统版本、构建方式
```
