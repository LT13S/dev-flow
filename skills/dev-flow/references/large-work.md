# 大规模任务：文档与分阶段

## 要写的文档

大规模任务都要写总纲、拍板记录（格式见 [handoff.md](handoff.md)）和阶段文档，放在档案约定的文档目录里，一个大任务一个子目录。碰到下面这些情况，对应的阶段文档里要多写一项：
- 不可逆的操作（数据迁移、删除数据、对外发布）→ 回滚或备份方案
- 涉及安全、权限、支付 → 要防什么、怎么验证
- 改动对外接口或跨系统的约定 → 怎么兼容旧的、要通知谁

## 怎么分阶段

- **按能独立验收的纵向切片来分。** 每个阶段都打通它涉及的所有层（数据 → 逻辑 → 界面），做完就能验收。不要按层来分（先写完所有模型，再写所有界面），那样要到最后才能验收，问题也最晚暴露。
- **每个阶段的量要能在一个会话里做完**，包括写阶段文档、实现和验证。放不下就再拆。
- **每个阶段做完都必须能编译通过，并且能按主流程第 5 步做端到端验证。** 做不到，说明切得太大，要再拆。
- **先做被别的阶段依赖的**；依赖程度相同时，先做最重要的。
- **现有结构让改动很别扭时，第一阶段先重构铺路。** 只做不改变行为的整理，做完照样要能编译，并验证行为没变：动手前先记下要对比的结果（命令输出、截图、日志），做完再跑一遍对比。
- **大范围的机械改动分批做。** 改名、改共享类型这类改动，没法按纵向切片保证每个阶段都能编译时，按这个顺序做：先加新写法、保留旧的 → 按目录或模块分批迁移调用方 → 没有调用方了再删旧的。每一步、每一批做完都能编译通过；一个阶段装几步或几批，按一个会话做得完来定。

## 总纲

只写蓝图：目标、不做什么、整体架构、阶段划分（每个阶段一句话说明，加上验收标准），以及每个阶段对应哪份文档。不写进度。

## 阶段文档（开工那个阶段时再写）

- 要改哪些文件和接口，打算怎么做
- 这个阶段做拍板摘要里的哪几条（写编号），完成前审查只核对这几条
- 不做什么
- 验收清单，最后一条是端到端验证：怎样证明整个功能真的能用
- 写到一个没看过之前对话的新会话，也能直接照着做

## 执行

- 拍板的窗口只写总纲和拍板记录，给开场白就停下；阶段 1 也在新窗口做，见 [handoff.md](handoff.md)。
- 一个阶段在一个会话里做完：阶段文档 → 实现 → 验证 → 审查 → 改完重测 → 交接 → 汇报。
- 阶段结束时，等审查回来、改完重测，再在阶段文档末尾写一段交接。第一行写「阶段 N/M 做完了；下一个是阶段 N+1/M：<一句话说做什么>」，下面写做完了什么、在哪个分支（开了工作树的写目录）、验证结果（测试结果文档在哪）、审查发现了什么及怎么处理的、遗留问题、下一个阶段要注意的坑。总纲里不写进度。
- 写完交接再一次汇报：开头写交接第一行那句，附上总纲和阶段文档的路径，接着是测试结果和主流程第 6 步的其余内容；最后问要不要提交、给开场白，提醒提交以后再开新会话。开场白是一句可以直接粘贴到新会话的话，比如「用 dev-flow 继续：先读 docs/xxx/总纲.md 和阶段 1 文档末尾的交接，开始做阶段 2/3」。
- 最后一个阶段做完时：
  - 先对照总纲，把每个阶段的验收标准过一遍，确认都做到了；没做到的写明。
  - 交接第一行和汇报开头写「阶段 M/M 做完了，整个任务做完了」，不给开场白。
  - 列出不在这个任务范围里、但上线前还要做的事，比如后端部署、隐私政策、发版前改回生产配置。
  - 写明总纲在哪个分支的哪个路径；开了工作树的，写明合并、删掉工作树以后去哪里看。
- 阶段做到一半，上下文就快满了（比如开始自动压缩），先把已完成的部分、改了哪些文件、下一步要做什么，写进阶段文档末尾的交接，同样给用户一句开场白，再开新会话接着做。
- 下一个阶段开一个新会话，从总纲和上一阶段的交接开始读；开工第一句话写「开始阶段 N/M：<一句话说做什么>」。
