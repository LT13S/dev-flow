# 开发流程

目标是又对又快，两者冲突时以对为准。
- **对**：动手前问清楚；能查的事实自己查；说"完成了"必须有刚跑出来的证据。
- **快**：决策一轮问完；实现不派子代理；验证频率看耗时；大范围搜索交给子代理，上下文留给实现。

## 0 定规模

先核对影响范围：改的是被多处调用的函数、公共组件或对外接口时，先搜调用方和依赖方，影响面大的直接按中、大规模处理。宁可开工前多花时间核对，也不要改到一半返工。

| 规模 | 判断标准 | 步骤 |
|---|---|---|
| 小 | 一句话说得清要改什么，且已确认影响范围小 | 1→4→5→6，不提问 |
| 中 | 多个文件、做法不止一种，或有要用户拍板的点 | 1→6 |
| 大 | 满足任一：跨模块又要分阶段、一个会话做不完、部分要等外部条件到位后另做 | 1→6，先读 [large-work.md](references/large-work.md) 再出方案，每个阶段单独开一个会话 |

拿不准按中等处理，别按大的来。

大规模：按能独立验收的功能切阶段，每阶段做完都能编译和验证；总纲（只写蓝图）和阶段文档放文档目录下的子目录；阶段结束写交接，给用户一句新会话的开场白。

## 1 读项目档案

从改动文件所在目录往上找 `.claude/project-profile.md`，沿途的都读；改动跨几个子项目时，每个子项目的都读。冲突时以离被改文件最近的为准；跨子项目时各部分按各自的档案，只能选一种做法的冲突（比如提交格式）问用户。

- 找到：命令、规矩和坑都以档案为准。
- 没找到：小规模跳过；中、大规模在调研之前先按 [profile-template.md](references/profile-template.md) 写出初稿，能推断的先填，推断不了的（比如 git log 里看不出的提交信息格式、档案要不要共享）标「待问」，第 3 步问完补全。初稿写好再进第 2 步，收尾时只往里追加。
- [技术栈指南](references/stacks/)：中、大规模读全文，小规模只读末尾「危险信号」表。按档案注明的读；没有档案就按改动的文件判断技术栈。

## 2 调研

- 划定范围再查。能用关键词直接定位的，自己搜；要摸清不熟悉的模块、预计要读十个以上文件时，派并行的只读子代理，各查一个方面，返回结论和 5～10 个关键文件，关键文件自己读一遍；不支持子代理就自己按关键词搜。
- 找已有的相似实现，照它的模式来。
- 查清影响范围：要改的函数、组件、接口被哪些地方用到，逐一列出，写进拍板摘要。
- 按任务读参考：照已有实现做（另一端、旧版本）→ [parity.md](references/parity.md)；涉及界面 → [ui-work.md](references/ui-work.md)；修 bug → [debugging.md](references/debugging.md)；大规模 → [large-work.md](references/large-work.md)。
- 查到能回答这四个问题为止：改哪些文件、照哪个已有实现、影响到哪些地方、还有什么要在第 3 步问。答不全继续查，答全就停。

## 3 一次拍板

- 按类找缺口：范围和不做什么、数据和状态、交互流程（空数据、加载中、出错）、边界和失败、兼容性、性能、怎么算完成。只问答案会改变做法或验收的。
- 只问用户才能定的：取舍、范围、偏好、只有用户知道的外部事实。项目规矩要求写单测时，要不要写单独问一题，推荐不写，项目规矩要求写也一样，写不写由用户定。
- **能查的自己查**：代码、配置、命令、文档能回答的不问。用户说的环境情况也要核实，对不上就作为问题提出来。查的时候不用干等，不依赖这个事实的问题照常先问。
- 一轮问完：用结构化提问工具一次问多个，没有这个工具就在回复里列编号的问题和选项；只单独问最影响做法和验收的，一轮最多 4 个，推荐项放第一，每题照这个格式写：「A（推荐）：一句理由；B：代价」。每题只问一件事，不在题里夹带追问。次要的、有合理默认的不单独问，列进拍板摘要的「默认做法」让用户一起确认。追问到所有会改变做法或验收的问题都有答案、没有用户没看到的假设为止。问题收不住，先给方案草图让用户改。
- 做法有明显分歧时（比如改动最小和结构最干净差别很大），给 2～3 个方案的对比和推荐，让用户选。
- 问题都有答案后，最后给拍板摘要（段名作小标题，每段从 1 编号，每条先写加粗小标题，细节拆成缩进圆点，写进用户的回答）：做什么、不做什么、默认做法、影响范围、依据的事实及怎么核实的、已知风险、怎么验收；新建了档案的写明在哪。给完就停下，等用户明确说开工再动手：回答问题、选了选项都不算确认。开工后中、大规模一律换新窗口实现，用户说直接做、上下文短也一样（拍板摘要里写明）：按 [handoff.md](references/handoff.md) 写拍板记录、给开场白就停下。

## 4 实现

- 动手前看 `git status` 和当前分支，记下已有的改动：可能是别的会话或别人的，不能覆盖，也不能混进自己的提交。
- 自己写，不派实现子代理（转交会丢信息）。
- 用工具自带的读文件、改文件功能，不用 `cat`、`sed`、重定向改代码：改文件工具会检查文件读过后有没有被别人改过，防止覆盖别的会话的改动；子目录的说明文件也只在用读文件功能读到时才加载。
- 中、大规模用待办清单跟踪。
- 只改需求范围内的，其他问题记下来收尾时提。
- 动手后发现事先没查到的情况：
  - 不改变已确认方案的小补漏（比如漏了一个调用方，改法完全一样）：直接补，汇报时单独列出。
  - 会改变方案、范围或影响面的（换做法、波及没确认的模块、改对外接口）：立即停下，说明发现了什么、建议怎么改、影响多大、有哪些备选，等确认再继续。拿不准就按这种处理。
  - 收尾时把这类遗漏追加进档案。
- 写法跟周围代码一致：命名、分层、注释密度、惯用写法。
- 功能日志打全，让验证有据可查：流程入口出口、分支走向、关键数据、状态变化、错误异常。用项目已有的日志方式，带统一的模块前缀，级别要在测试用的包里看得到（看档案），不打密码、令牌。这些日志保留，和修 bug 的临时调试日志不同。
- 新建文件后按档案做登记（改工程文件、装依赖、重新生成代码等）。

## 5 验证

**频率看耗时**：秒级的（类型检查、单个测试文件、lint）每改完一块就跑；几分钟以上的（原生编译、整包构建、全量测试、端到端验证）阶段末尾统一跑。小改动：
- 只动文案、配置值、资源：格式检查加搜一下引用即可，汇报写一行「未编译：没跑 <完整编译命令>，只做了 <哪些检查>」。
- 动了代码逻辑：要编译或测试通过才算完成；编译要几分钟以上时，可以先汇报「未编译」，由用户决定现在编还是攒着一起编，但提交前必须编过。

**拿证据说话**：
- 说"通过""修好了""完成了"之前，必须刚刚跑过能证明它的命令，看过完整输出和退出码。汇报时附上命令和关键结果（退出码、通过数量、截图）：每个「通过」在聊天汇报里都跟上命令和退出码，一行就够，详细输出放测试结果文档。上一次的结果、"应该没问题"都不算。能证明问题解决的关键场景还没跑过（比如要等用户配合那一步），只能说「改完了、还没验证」，写明差哪一步、要用户做什么，验证完再说「修好了」。
- 结果只代表跑的那一刻。跑完之后又改过代码，或者别的会话改了相关文件，就要重跑。
- 子代理说做完了，要自己看 git diff 和验证输出来核实。让子代理跑耗时命令时，要求它前台阻塞等待结果：子代理一结束，它放到后台的进程会被一起终止。

**端到端验证自己做**：默认不新写测试代码，单测也不写（项目规矩要求的，按第 3 步问的结果办）；已有的自动化测试照常跑。把程序跑起来实际操作：App 用档案里的自动化工具点按、截图，接口用 curl 调，同时看日志。按「场景 → 操作 → 预期」逐条验证，每条附截图或日志。
- 只有自动化做不到的步骤才请用户配合（连接实体设备、输入密码或验证码、扫码、解锁手机）：到那一步再叫，处理好后接着测；不能因此把整段测试交给用户。
- 没法自动判断的结果（震动、声音这类靠人感受的），单独列出请用户确认，并说明原因。
- 测完出一份测试结果文档，格式见 [test-report.md](references/test-report.md)。小改动挑一两个关键场景，不用写文档，在汇报里逐条写测了什么、命令和结果；有截图时才写。

**完成前审查**（中、大规模）：只审这次自己的改动（对照第 4 步记下的状态）。用工具自带的代码审查查 bug（比如 `/code-review`），没有就派子代理只看改动找 bug；再对照拍板摘要逐条核对需求、边界情况，以及范围外有没有被改动。只修影响正确性和需求的问题，风格意见可以不改，别过度设计。

## 6 收尾

- 汇报：改了什么（含动手后补的遗漏）、拍板摘要逐条做到了没有（中、大规模；在测试结果文档里按摘要编号逐条列，依据、影响范围、已知风险三段不列，每条标做到 / 没做到 / 有调整；汇报里写几条做到，没做到和有调整的逐条说明）、测试结果文档在哪（通过、失败、需人工确认各几项）、审查发现了什么及怎么处理的、范围外发现的问题、还有哪些没验证或有风险。
- 问用户是否提交，附上按档案格式写的提交信息（类型只用档案列出的；没有合适的，给出建议并请用户定）。同意后才提交：先单独跑一次 `git status` 和 `git diff`（不要和 `git commit` 串在一条命令里），对照第 4 步记下的状态，只提交自己的改动；相关文件在验证之后被别人改过，先重跑验证。动了代码逻辑的，提交前确认最后一次改代码之后，档案里最完整的那道编译或构建跑通过；没跑过就先跑，通过了再提交。不推送，除非用户明确要求。
- 收尾时回顾：档案里的命令能不能照原样跑通（要不要先设环境变量、装依赖、换参数）、有没有档案没写或写错的事实；不管是踩了才发现还是提前看出来的，都追加进档案对应的小节，并在汇报里说一句。换个同技术栈的项目也会遇到的，提醒用户补进技术栈指南。

## 危险信号

| 冒出这个念头 | 实际应该 |
|---|---|
| 先把相关文件都读一遍 | 划定范围，大范围交给子代理 |
| 需求有歧义，先按我的理解做 | 回第 3 步问 |
| 没有档案，收尾时再写 | 调研前先写初稿，收尾只往里追加 |
| 用户答完问题了，直接开工 | 先给拍板摘要，等用户明确说开工 |
| 项目有单测，顺手补几条 | 默认不写，项目要求的先单独问 |
| 用户说环境是 X，直接照用 | 能查先查 |
| 文档或注释说它是 X | 以代码和实测为准 |
| 派个子代理去写，我来审 | 中小任务自己写更快 |
| 只改了几行，影响不大 | 先搜调用方，确认影响范围 |
| 顺手把旁边也重构了 | 只改范围内的，其余记下来 |
| 每改一行就编译一次 | 看耗时，慢的攒到阶段末尾 |
| 应该没问题，不用验证了 | 做相称的验证 |
| 编译刚才通过了，可以汇报 | 之后代码变过就重跑 |
| 改完了，告诉用户修好了 | 关键场景验证过了吗？没验证只能说「改完了、还没验证」 |
| 子代理说它做完了 | 看 git diff 和验证输出 |
| 有一步要人工，整段交给用户测 | 只请用户做那一步，其余自己测 |
| 这个分支不太会走到，不用打日志 | 关键分支都打日志，测试时才能证明走对了 |
| 修了两次没好，再猜一次 | 停止猜测，按 debugging.md 拿数据 |
| 审查意见全都得改 | 只改影响正确性和需求的 |
| 把所有改动都加进来提交 | 只提交自己改的文件，对照第 4 步记下的状态 |
| 同一个问题被用户纠正了两次 | 停下来总结教训，把完整需求复述给用户确认后再改；如果这个会话已经来回改了很多轮、上下文很长，建议用户开新会话，并给出一段带上教训的开场说明 |
